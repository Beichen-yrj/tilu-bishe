# 铁路危险货物运输“双重预防机制”一体化信息平台部署指南

> 适用项目：`daima/`
>
> 当前技术栈：React 19 + TypeScript + Vite 8（前端）、Python + FastAPI + SQLAlchemy + PyMySQL（后端）、MySQL 8（数据库）。
>
> 推荐环境：Ubuntu 22.04 LTS、Nginx、systemd。本文只提供部署步骤和清理方案，不包含真实服务器地址、密码、JWT 密钥或 AI API Key。

---

## 一、先确认部署边界

### 1.1 本项目实际架构

```text
用户浏览器
    |
    | HTTPS :443 / HTTP :80
    v
Nginx
  /       -> /var/www/rail-safety（Vite dist）
  /api/   -> 127.0.0.1:8000（FastAPI）
                         |
                         v
                 MySQL 8：rail_safety
```

| 组件 | 生产运行方式 | 监听地址 | 说明 |
| --- | --- | --- | --- |
| React/Vite | `npm run build` 后由 Nginx 提供静态文件 | 不单独监听公网 | 构建目录为 `daima/dist` |
| FastAPI | `uvicorn app.main:app` + systemd | `127.0.0.1:8000` | 工作目录必须是 `daima/backend` |
| MySQL | Ubuntu systemd 服务 | `127.0.0.1:3306` | 使用专用应用账号，不用 root 运行应用 |
| AI 助手 | FastAPI 按需调用 DeepSeek | 出站 HTTPS | 不配置 `DEEPSEEK_API_KEY` 时接口返回未配置，不影响基础平台 |

仓库中的 `daima/docker-compose.yml` 只用于本地开发 MySQL，使用 `rail-safety-mysql` 容器、宿主机 `3307` 和开发密码。生产环境不要直接沿用这些开发参数，也不要把 `3307` 暴露到公网。

### 1.2 当前可确认与待确认事项

- 源码可确认：前端构建命令是 `npm run build`，API 健康检查为 `GET /api/health`，后端默认端口为 `8000`。
- 源码可确认：后端启动时会创建缺失表并执行兼容字段补齐；正式变更前仍应先备份数据库。
- 源码可确认：评估照片、整改照片和头像以数据库字段保存，数据库备份不能省略。
- 待确认：阿里云实例公网 IP、域名、HTTPS 证书、服务器登录账号、正式数据库密码、管理员密码和是否启用 AI。
- 本文未执行云端命令，因此“已部署、已云端验证、已上线”均不能由本文推出。

### 1.3 正式公网开放前的安全门禁

当前源码可部署到受控测试环境，但还不能仅凭构建和测试结果判定为生产就绪：

- 当前公开注册接口允许注册者自行选择安全管理员或项目经理角色。正式开放前必须改为默认最低权限，并由管理员在服务端授权高权限角色，或关闭公开注册。
- 登录和注册接口尚需结合实际网络边界配置限流、失败锁定、告警和审计。
- `ADMIN_PASSWORD` 必须在首次启动前设置强密码；不得使用源码或 SQL 中的演示默认值。
- AI 功能会把脱敏后的业务摘要发送到所配置的外部模型服务。启用前需确认数据分类、隐私与单位合规要求。
- 应完成数据库恢复演练、权限矩阵测试、浏览器/设备验证、漏洞与依赖检查，再判断是否可以公网生产上线。

在这些门禁完成前，推荐只在内网、VPN、固定 IP 白名单或其他受控访问边界内试用。

## 二、服务器与安全组

### 2.1 推荐配置

| 配置项 | 最低 | 推荐 |
| --- | --- | --- |
| CPU | 2 核 | 4 核 |
| 内存 | 4 GB | 8 GB |
| 系统盘 | 40 GB | 80 GB |
| 带宽 | 5 Mbps | 10 Mbps |
| 系统 | Ubuntu 22.04 LTS | Ubuntu 22.04 LTS |

### 2.2 阿里云安全组入方向

只开放必要端口：

| 端口 | 来源 | 用途 |
| --- | --- | --- |
| 22/tcp | 仅管理员固定 IP（推荐） | SSH |
| 80/tcp | `0.0.0.0/0` | HTTP、证书签发 |
| 443/tcp | `0.0.0.0/0` | HTTPS |

不要开放 `3306`、`8000`、`3307`。FastAPI 和 MySQL 只监听本机回环地址，由 Nginx 统一对外提供服务。

## 三、安装基础环境

### 3.1 SSH 登录和系统更新

```bash
ssh root@你的公网IP
apt update && apt upgrade -y
```

### 3.2 安装系统依赖

```bash
apt install -y ca-certificates curl wget git vim rsync \
  python3 python3-venv python3-pip mysql-server nginx \
  certbot python3-certbot-nginx ufw
```

### 3.3 安装 Node.js 20 LTS 或更高版本

当前项目的 Vite 依赖要求 Node `20.19+` 或 `22.12+`。Ubuntu 22.04 自带 Node 版本可能过旧，不要直接使用系统旧版本构建。

```bash
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs
node -v
npm -v
```

如果 `node -v` 低于 `v20.19.0`，先升级后再执行前端构建。

### 3.4 创建运行用户和目录

```bash
useradd --system --home /opt/rail-safety --shell /usr/sbin/nologin railapp
mkdir -p /opt/rail-safety /var/www/rail-safety /opt/backups/rail-safety
chown -R railapp:railapp /opt/rail-safety /var/www/rail-safety
chmod 750 /opt/rail-safety
```

### 3.5 配置 GitHub SSH（如果通过 Git 拉取）

以下命令使用服务器自己的密钥，不要把个人电脑私钥上传到服务器：

```bash
sudo -u railapp mkdir -p /opt/rail-safety/.ssh
sudo -u railapp chmod 700 /opt/rail-safety/.ssh
sudo -u railapp ssh-keygen -t ed25519 -C "rail-safety-server" \
  -f /opt/rail-safety/.ssh/id_ed25519 -N ""
cat /opt/rail-safety/.ssh/id_ed25519.pub
```

把输出的公钥添加到 GitHub 的 Deploy Key（按仓库需要选择只读权限），然后测试：

```bash
sudo -u railapp GIT_SSH_COMMAND="ssh -i /opt/rail-safety/.ssh/id_ed25519" \
  ssh -T git@github.com
```

## 四、配置 MySQL

### 4.1 启动并设置开机启动

```bash
systemctl enable --now mysql
systemctl status mysql --no-pager
mysql_secure_installation
```

### 4.2 创建生产数据库和专用账号

密码仅在交互式输入时提供，不要把真实密码提交到 Git 或写进公开文档。

```bash
sudo mysql
```

```sql
CREATE DATABASE IF NOT EXISTS rail_safety
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS 'rail_app'@'localhost' IDENTIFIED BY '替换为随机强密码';
ALTER USER 'rail_app'@'localhost' IDENTIFIED BY '替换为随机强密码';
GRANT ALL PRIVILEGES ON rail_safety.* TO 'rail_app'@'localhost';
FLUSH PRIVILEGES;
EXIT;
```

如服务器已有 `rail_safety` 数据库，先确认它是否属于本项目，不要直接覆盖或删除。

### 4.3 生产环境不要直接执行演示初始化脚本

当前 `backend/init_db.sql` 包含演示管理员 `admin / admin123456`，重复执行还会把同名管理员密码改回该演示密码。因此，生产首次部署不要执行这个 SQL 文件。

按第六节先设置强 `ADMIN_PASSWORD`，FastAPI 首次启动会通过 SQLAlchemy 创建缺失表，并用生产环境变量创建管理员。启动前必须确保 `rail_app` 对 `rail_safety` 有建表和兼容迁移所需权限。

只有迁移既有演示数据时，才应在完成备份后人工审阅 SQL，移除演示管理员语句，再在隔离环境验证后执行。不要在生产数据库上直接试跑。

## 五、拉取项目代码

下面的仓库地址是占位符，替换为实际仓库和分支；不要把带密码的 HTTP 仓库地址写进命令或文档。

```bash
cd /opt/rail-safety
sudo -u railapp git clone --branch main --single-branch \

cd /opt/rail-safety/daima
sudo -u railapp git status --short --branch
```

如果目录已经存在，先检查当前分支、远程地址和未提交改动：

```bash
git status --short --branch
```

## 六、部署 FastAPI 后端

### 6.1 创建虚拟环境并安装依赖

```bash
cd /opt/rail-safety/daima/backend
sudo -u railapp python3 -m venv .venv
sudo -u railapp .venv/bin/python -m pip install --upgrade pip
sudo -u railapp .venv/bin/pip install -r requirements.txt \
  -i https://mirrors.aliyun.com/pypi/simple/
```

### 6.2 创建生产环境变量文件

```bash
sudo -u railapp vim /opt/rail-safety/daima/backend/.env
chmod 600 /opt/rail-safety/daima/backend/.env
```

内容模板如下，所有示例值都必须替换：

```dotenv
APP_ENV=production
DATABASE_URL=mysql+pymysql://rail_app:替换为URL编码后的数据库密码@127.0.0.1:3306/rail_safety?charset=utf8mb4
JWT_SECRET=替换为至少32位随机密钥
ACCESS_TOKEN_MINUTES=480
CORS_ORIGINS=https://你的域名
ADMIN_USERNAME=admin
ADMIN_PASSWORD=替换为首次登录后立即更换的强密码

# 不启用 AI 时保留为空；启用时再填写真实密钥
DEEPSEEK_API_KEY=
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-chat
```

生成 JWT 密钥示例：

```bash
openssl rand -base64 64
```

`DATABASE_URL` 中的密码属于 URL 的一部分。密码若含 `@`、`:`、`/`、`?`、`#`、`%` 等字符，必须先做百分号编码；不确定时可为数据库账号生成只含大小写字母和数字的足够长随机密码。不要把未编码的特殊字符直接拼进连接串。

注意：`backend/.env` 已被 `.gitignore` 忽略；不要执行 `git add -f backend/.env`。

### 6.3 创建 systemd 服务

```bash
vim /etc/systemd/system/rail-safety-api.service
```

```ini
[Unit]
Description=Rail Safety FastAPI API
After=network.target mysql.service
Wants=mysql.service

[Service]
Type=simple
User=railapp
Group=railapp
WorkingDirectory=/opt/rail-safety/daima/backend
EnvironmentFile=/opt/rail-safety/daima/backend/.env
ExecStart=/opt/rail-safety/daima/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=always
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

启动并检查：

```bash
systemctl daemon-reload
systemctl enable --now rail-safety-api
systemctl status rail-safety-api --no-pager
curl http://127.0.0.1:8000/api/health
journalctl -u rail-safety-api -n 100 --no-pager
```

健康检查应包含：

```json
{"status":"ok","database":"connected"}
```

如果出现数据库连接错误，先检查 `.env` 的账号、密码、库名和 MySQL 状态，不要通过把数据库暴露到公网来绕过问题。

## 七、构建并部署 React 前端

### 7.1 安装依赖并构建

```bash
cd /opt/rail-safety/daima
sudo -u railapp npm ci
sudo -u railapp env VITE_API_BASE_URL=/api npm run build
```

构建完成后应存在 `/opt/rail-safety/daima/dist/index.html`。当前 Vite 配置生产构建使用相对资源路径，适合由 Nginx 提供静态文件。

### 7.2 发布静态文件

```bash
rsync -a --delete /opt/rail-safety/daima/dist/ /var/www/rail-safety/
chown -R www-data:www-data /var/www/rail-safety
find /var/www/rail-safety -type d -exec chmod 755 {} \;
find /var/www/rail-safety -type f -exec chmod 644 {} \;
```

`rsync --delete` 会删除目标目录中不属于本次构建的文件。确认目标目录就是本项目的静态目录后再执行。

## 八、配置 Nginx

```bash
vim /etc/nginx/sites-available/rail-safety
```

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name 你的域名;   # 没有域名时临时填写公网 IP 或 _

    root /var/www/rail-safety;
    index index.html;
    charset utf-8;
    client_max_body_size 20M;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
        proxy_connect_timeout 15s;
    }
}
```

启用站点并验证：

```bash
ln -s /etc/nginx/sites-available/rail-safety /etc/nginx/sites-enabled/rail-safety
# 仅当 default 未承载任何其他站点时才删除：
rm -f /etc/nginx/sites-enabled/default
nginx -t
systemctl reload nginx
curl -I http://127.0.0.1/
curl http://127.0.0.1/api/health
```

如果服务器上还有其他站点，不要删除 `default` 或其他配置，先列出实际启用的符号链接并确认域名归属。

## 九、配置 HTTPS

前提：域名的 A/AAAA 记录已经解析到本机，且 80/443 已放行。

```bash
certbot --nginx -d 你的域名
```

证书配置完成后，把 `CORS_ORIGINS` 改为最终 HTTPS 域名并重启后端：


## 十二、日常运维和更新

### 12.1 查看服务与日志

```bash
systemctl status nginx mysql rail-safety-api --no-pager
journalctl -u rail-safety-api -f
tail -f /var/log/nginx/access.log /var/log/nginx/error.log
```

### 12.2 更新部署

仓库现提供 `update.sh` 和 `backup.sh`。将新增脚本提交并推送到 GitHub，再在服务器首次执行 `sudo -H -u railapp git -C /opt/rail-safety/daima pull --ff-only origin main` 获取脚本。之后每次 GitHub 更新代码，只需运行：

```bash
sudo bash /opt/rail-safety/daima/update.sh
```

脚本自动备份、拉取 `origin/main`、构建前端、安装后端依赖、重启铁路 API 并检查数据库健康；保留生产 `.env`、管理员账号和业务数据。完整使用说明位于 `daima/服务器脚本使用说明.md`。旧 `meitan` 项目继续保留，不受脚本影响。

以下为不使用脚本时的手动流程：

先备份数据库，再更新代码和依赖：

```bash
mkdir -p /opt/backups/rail-safety
mysqldump -u rail_app -p --single-transaction --routines --events \
  rail_safety > /opt/backups/rail-safety/rail_safety_$(date +%Y%m%d_%H%M%S).sql
tar -czf /opt/backups/rail-safety/web_$(date +%Y%m%d_%H%M%S).tar.gz \
  -C /var/www/rail-safety .

cd /opt/rail-safety/daima
git pull --ff-only origin main
sudo -u railapp backend/.venv/bin/pip install -r backend/requirements.txt
sudo -u railapp npm ci
sudo -u railapp env VITE_API_BASE_URL=/api npm run build
rsync -a --delete dist/ /var/www/rail-safety/
systemctl restart rail-safety-api
systemctl reload nginx
curl http://127.0.0.1:8000/api/health
```

如果 `git pull`、数据库升级或构建失败，保留日志和当前版本，不要用强制重置覆盖现场；先恢复服务，再单独处理失败原因。

### 12.3 数据库备份与恢复

一键备份（无需把密码写入脚本）：

```bash
sudo bash /opt/rail-safety/daima/backup.sh
```

脚本使用 MySQL root 本机 socket 认证，备份 `rail_safety` 数据库、生产 `.env`、源码、前端和铁路部署配置，存放在 `/opt/backups/rail-safety/rail-safety_时间_随机后缀/`。仅有 `COMPLETE` 标记的目录才表示本次备份全部完成；备份含密钥和业务数据，应限制访问并另存一份到服务器外。

手动备份：

```bash
mysqldump -u rail_app -p --single-transaction rail_safety \
  > /opt/backups/rail-safety/rail_safety_$(date +%Y%m%d_%H%M).sql
```

恢复前先停止写入服务并确认备份文件来源：

```bash
systemctl stop rail-safety-api
mysql -u rail_app -p rail_safety < /opt/backups/rail-safety/rail_safety_YYYYMMDD_HHMM.sql
systemctl start rail-safety-api
curl http://127.0.0.1:8000/api/health
```

每天定时备份可以使用 root 的 crontab，但密码不要直接写进命令行；建议使用受限权限的 MySQL 客户端配置文件，并限制文件权限为 `600`。

### 12.4 回滚原则

- 更新前记录 `git rev-parse HEAD`，保留数据库备份和当前 `/var/www/rail-safety` 归档。
- 前端异常时可先恢复上一个静态文件归档，再执行 `nginx -t && systemctl reload nginx`。
- 后端异常时切回已知可用的 Git 提交，重装该提交锁定的依赖并重启 `rail-safety-api`。
- 数据库恢复会覆盖更新后的数据，必须先停止写入、确认备份时间点和影响范围，再单独授权执行。
- 当前应用启动包含自动建表和兼容字段补齐，不等于完整迁移/回滚系统；涉及结构变更时应先在测试库演练。

## 十三、清理服务器上已有的 `meitan` 项目

> 这一节只清理旧项目，不要直接在未盘点的服务器上复制粘贴全部删除命令。新项目通常仍需要 Nginx、MySQL、Git、Python 等公共组件，不能因为 `meitan` 退出就卸载这些软件。

推荐顺序是：盘点旧项目 -> 备份旧数据 -> 部署并验证新项目的独立端口 -> 切换 Nginx -> 观察一段时间 -> 停止旧服务 -> 最后删除旧文件和数据库。若新旧项目复用同一域名，不要同时启用两个相同 `server_name` 的 Nginx 配置。

### 13.1 先盘点，不修改任何东西

```bash
systemctl list-unit-files --type=service | grep -i meitan || true
systemctl list-units --type=service --all | grep -i meitan || true
docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}' | grep -i meitan || true
ss -ltnp
find /etc/nginx/sites-enabled /etc/nginx/sites-available -maxdepth 1 \
  -iname '*meitan*' -print 2>/dev/null
find /opt /var/www -maxdepth 2 -iname '*meitan*' -print 2>/dev/null
grep -Ril 'meitan' /etc/systemd/system /etc/nginx 2>/dev/null || true
crontab -l 2>/dev/null | grep -i meitan || true
grep -Ril 'meitan' /etc/cron.d /etc/cron.daily /etc/cron.weekly 2>/dev/null || true
certbot certificates 2>/dev/null || true
```

记录以下事实后再继续：服务单元名称、代码目录、前端目录、Nginx 站点文件、监听端口、Docker Compose 目录、数据库名和备份位置。不能仅凭目录名判断数据库可以删除。

### 13.2 先备份旧项目数据（如需保留）

```bash
mkdir -p /opt/backups/meitan-retirement

# 根据盘点结果替换数据库名和账号；不要把真实密码写在命令中
mysqldump -u 旧项目数据库账号 -p --single-transaction 旧项目数据库名 \
  > /opt/backups/meitan-retirement/meitan_$(date +%Y%m%d_%H%M%S).sql

# 如有上传目录或配置，先打包留档；先确认这些路径确实存在且属于旧项目
tar -czf /opt/backups/meitan-retirement/meitan-files_$(date +%Y%m%d_%H%M%S).tar.gz \
  /opt/meitan /opt/meitan-server /var/www/meitan 2>/dev/null || true
```

备份文件可以恢复后再删除。若旧项目数据无需保留，也建议至少保留一次最终备份，等待业务负责人确认后再清理。

### 13.3 停止并禁用旧服务

下面的服务名必须以 13.1 的实际盘点结果为准；参考项目中常见的名称可能是 `meitan-server`、`meitan-python`，但不要盲目假定：

```bash
systemctl stop meitan-server meitan-python 2>/dev/null || true
systemctl disable meitan-server meitan-python 2>/dev/null || true
systemctl reset-failed meitan-server meitan-python 2>/dev/null || true
```

确认端口已释放：

```bash
ss -ltnp | grep -E ':8080|:5000' || true
```

### 13.4 删除旧 systemd 配置

只有确认服务已经停止、备份完成、文件确实属于旧项目后，才执行：

```bash
rm -f /etc/systemd/system/meitan-server.service
rm -f /etc/systemd/system/meitan-python.service
systemctl daemon-reload
```

如果盘点发现使用了其他 unit 名称，按实际文件名处理。不要删除 `mysql.service`、`nginx.service`、`ssh.service` 或本项目的 `rail-safety-api.service`。

### 13.5 删除旧 Nginx 站点配置

先查看内容和符号链接指向：

```bash
ls -l /etc/nginx/sites-enabled /etc/nginx/sites-available
sed -n '1,220p' /etc/nginx/sites-available/meitan
```

确认域名不再指向旧项目后：

```bash
rm -f /etc/nginx/sites-enabled/meitan
rm -f /etc/nginx/sites-available/meitan
nginx -t
systemctl reload nginx
```

如果旧站点与其他项目共用一个配置文件，只删除对应 `server` 块，不要删除整个文件。

如果旧域名不再使用，可在确认没有其他站点复用该证书后执行 `certbot delete --cert-name 证书名称`。如果新项目继续使用原域名和证书，则不要删除证书。

### 13.6 删除代码、虚拟环境和静态文件

先用绝对路径确认目标，再逐项删除。以下路径只是参考项目指南中的常见路径，必须按 13.1 的盘点结果替换：

```bash
ls -ld /opt/meitan /opt/meitan-server /var/www/meitan
```

确认无误后再执行：

```bash
rm -rf /opt/meitan
rm -rf /opt/meitan-server
rm -rf /var/www/meitan
```

不要执行 `rm -rf /opt/*`、`docker system prune -a --volumes` 或类似全局清理命令；这些命令可能删除本项目、其他项目或数据库数据。

参考项目还可能使用 `/opt/uploads`。这个名称过于通用，只有在检查旧配置、文件内容和其他服务引用并确认它完全属于 `meitan` 后才能归档或删除；不能仅凭名称直接清理。同时移除经盘点确认只属于旧项目的定时更新或备份任务。

### 13.7 Docker 旧项目清理（仅当盘点确认使用 Docker）

进入旧项目的实际 Compose 目录，先查看服务和卷：

```bash
cd /旧的/meitan/compose目录
docker compose ps -a
docker volume ls | grep -i meitan || true
```

停止并删除容器、网络：

```bash
docker compose down
```

只有确认卷内数据库或上传文件已经备份、且不再需要，才追加 `--volumes`：

```bash
docker compose down --volumes
```

不要对整台服务器执行带 `--volumes` 的全局 prune。

### 13.8 数据库和 MySQL 账号清理（最后一步，需单独确认）

先列出数据库和授权：

```bash
sudo mysql -e "SHOW DATABASES;"
sudo mysql -e "SELECT User,Host FROM mysql.user;"
```

确认旧项目数据库不被新项目或其他服务使用，再执行：

```sql
DROP DATABASE `旧项目数据库名`;
DROP USER '旧项目数据库账号'@'localhost';
FLUSH PRIVILEGES;
```

数据库删除是不可逆操作，必须在业务负责人明确确认并完成可恢复备份后执行。新项目使用的是 `rail_safety` 和 `rail_app`，不要因为清理 `meitan` 而删除这两个对象。

### 13.9 清理完成后的检查

```bash
systemctl list-units --type=service --all | grep -i meitan || true
find /etc/nginx/sites-enabled /etc/nginx/sites-available -maxdepth 1 \
  -iname '*meitan*' -print 2>/dev/null
ss -ltnp
systemctl status nginx mysql rail-safety-api --no-pager
curl http://127.0.0.1:8000/api/health
```

应确认：旧服务不再运行、旧站点不再启用、旧端口不再监听、新项目 API 健康检查正常；不能只凭“目录已删除”判断清理完成。
