## 3 项目背景与目标

### 3.1 现状问题

铁路危险货物运输隐患排查与风险管控目前仍较多依赖纸质表格、Excel 人工统计和线下主观打分，存在以下问题：

- 静态设施隐患与动态作业风险分散管理，缺少统一入口；
- 人工评分口径不一致，风险等级缺少可追溯的量化依据；
- 评估结果、整改过程和复核结论未形成完整闭环；
- 历史数据分散，难以分析风险变化、薄弱环节和整改效果；
- 管理人员无法通过网页随时查看评估与整改进展；
- 现场照片仍依赖人工判断，尚未形成智能识别能力。

### 3.2 建设目标

系统应实现以下目标：

1. 建立静态隐患和动态作业风险相结合的统一评估流程；
2. 通过 5×5 风险矩阵实现风险量化、分级和可视化；
3. 引入安全工程师、项目经理等专业人员的评估与确认；
4. 将评估结果自动转化为可执行的整改任务，并全过程记录进度；
5. 建立双人复核和销号机制，实现隐患治理闭环；
6. 保存历次评估、整改和确认数据，支持多维统计分析；
7. 以网页形式部署，使授权用户能够在线访问和及时查看最新数据；
8. 形成专业、清晰、具有铁路安全行业特征的可视化界面；
9. 为后续现场照片隐患识别和模型训练预留数据与接口基础。

## 4 建设范围

### 4.1 本期范围

- 用户登录、用户中心、角色和权限管理；
- 评估任务创建、分派、保存、提交和查询；
- 静态风险评估；
- 动态风险评估；
- 安全工程师和项目经理专业意见；
- 5×5 风险矩阵与综合风险结果；
- 问题识别和详细整改建议；
- 整改任务、分阶段进度、证据上传、复核和销号；
- 历史数据归档、检索、筛选和导出；
- 折线图、雷达图、散点图等统计分析；
- 网页部署、数据持久化、权限控制和操作审计；
- 指标库、法规依据和整改模板的后台维护。

### 4.2 后续扩展范围

- 上传现场照片后自动识别安全帽佩戴、通道堵塞、警示标识缺失等问题；
- 图片标注、样本审核、训练集版本和模型版本管理；
- 视频流实时识别、传感器和铁路调度系统对接；
- 短信、企业微信等外部消息通知。

上述扩展能力不作为本期核心版本的完成条件，但本期数据结构应保留附件、识别结果和人工复核字段。

## 5 现有系统基线

现有材料表明，系统 1.0 已具备以下基础：

- 技术形态为 Python Flask、SQLite、原生 HTML/CSS/JavaScript；
- 具备注册、登录、修改密码和会话鉴权；
- 静态自查共 31 项，实际覆盖 8 类：站台结构、平面布局、站台设施布局、轨道、警示标识、安全距离、站台设施设备、监控报警设备；
- 动态评估共 61 项，覆盖进场、装卸、搬运三个环节，以及人、物、环境、管理四类因素；
- 每个评估指标关联法规或标准依据；
- 动态评估支持可能性 L、严重度 C 和风险值 R 的计算；
- 已有综合结果、风险矩阵、风险等级分布和高风险项展示；
- 已有隐患台账及“未整改、整改中、已闭环”状态；
- 已有仪表盘、历史评估记录和打印入口。

下一阶段应优先在现有能力上演进，避免重复建设；数据库和可视化技术是否升级，应由部署规模和后续维护要求决定。

## 6 用户角色与权限

| 角色 | 主要职责 | 关键权限 |
| --- | --- | --- |
| 系统管理员 | 维护系统、用户、指标和基础数据 | 用户与角色管理、指标库维护、法规维护、整改模板维护、全量数据查看、系统配置、审计查询 |
| 评估发起人 | 创建并组织评估 | 新建任务、选择场所和范围、分派评估人员、查看任务进度、提交评估 |
| 现场评估人员 | 完成静态和动态检查 | 填写检查项、录入参数、上传附件、暂存和提交本人负责的评估内容 |
| 安全工程师 | 提供专业判断并复核整改 | 提交专业意见、查看系统评分、提出补充问题、确认或驳回整改 |
| 项目经理 | 负责管理确认和闭环审批 | 查看评估结果、确定责任人与期限、确认或驳回整改、完成最终销号确认 |
| 整改责任人 | 执行整改任务 | 查看本人任务、更新阶段、填写说明、上传证据、申请复核 |
| 只读查看人 | 查看授权范围内的数据 | 查看仪表盘、结果、台账和统计图，不得修改业务数据 |

权限应同时受角色、所属组织、项目或场站数据范围限制。任何角色不得查看其授权范围之外的敏感评估记录。

## 7 总体业务流程

1. 评估发起人创建评估任务，填写组织、场站、作业区域、危险货物类别、评估时间和参与人员；
2. 系统加载对应版本的静态 31 项和动态 61 项指标；
3. 现场评估人员完成静态检查、动态参数和 L/C 评分，并上传必要证据；
4. 系统实时计算单项风险值与风险等级，展示 5×5 风险矩阵；
5. 安全工程师和项目经理分别提交专业意见；
6. 系统生成综合结果、问题清单和逐项整改建议；
7. 评估确认后，问题自动转入整改模块，生成责任、措施、资金、时限、预案相关字段；
8. 整改责任人按问题专属阶段更新进度并提交证据；
9. 安全工程师完成技术复核，项目经理完成管理确认；
10. 两方均确认后问题销号，评估任务在全部问题销号后闭环；
11. 评估、整改、复核和销号全过程进入历史数据库，并用于趋势和对比分析。

## 8 功能需求

### 8.1 用户认证与用户中心

| 编号 | 需求 |
| --- | --- |
| FR-USER-001 | 用户应能够使用账号和密码登录，未登录访问业务页面时应跳转到登录页。 |
| FR-USER-002 | 系统应支持修改密码、退出登录和查看本人基本资料。 |
| FR-USER-003 | 管理员应能够创建、停用、启用用户并分配角色和数据范围。 |
| FR-USER-004 | 用户中心应展示本人待评估任务、待整改任务、待复核任务和最近操作记录。 |
| FR-USER-005 | 密码不得明文存储；连续登录失败应触发限流或临时锁定。 |
| FR-USER-006 | 关键业务操作应记录操作人、时间、对象和变更前后状态。 |
| FR-USER-007 | 用户从门户点击任一“进入管理平台”入口时，系统应在当前页面弹出登录/注册面板；认证成功后才进入业务平台。 |
| FR-USER-008 | 账号保存于 MySQL，密码使用服务端摘要，登录成功签发会话令牌；前端不得将密码写入 localStorage 或 sessionStorage。 |
| FR-USER-009 | 认证接口应提供注册、登录、当前用户、退出登录和修改密码能力；失效或退出的会话不得继续访问业务接口。 |

### 8.2 评估任务管理

| 编号 | 需求 |
| --- | --- |
| FR-TASK-001 | 系统应支持新建、暂存、分派、提交、撤回和查看评估任务。 |
| FR-TASK-002 | 新建任务至少包含任务名称、组织、场站、区域、危险货物类别、评估范围、计划时间和参与人员。 |
| FR-TASK-003 | 系统应为任务生成唯一编号，并记录所使用的指标库版本和风险规则版本。 |
| FR-TASK-004 | 同一任务应同时包含静态评估、动态评估、专家意见、综合结果和整改台账。 |
| FR-TASK-005 | 系统应按草稿、评估中、待专家意见、待确认、整改中、待复核、已闭环、已取消管理任务状态。 |
| FR-TASK-006 | 任务应支持按组织、场站、人员、日期、状态和风险等级检索。 |

### 8.3 指标库与法规库

| 编号 | 需求 |
| --- | --- |
| FR-LIB-001 | 系统应内置静态 31 项和动态 61 项指标，并保留每项法规依据。 |
| FR-LIB-002 | 指标应包含编号、类型、环节或类别、维度、危险源、检查说明、参数类型、法规依据、默认整改模板和启停状态。 |
| FR-LIB-003 | 管理员应能够通过模板导入 Excel 指标数据；导入前应校验必填列、重复编号、枚举值和法规关联。 |
| FR-LIB-004 | 指标变更应形成新版本，历史评估继续引用原版本，不得被新版本覆盖。 |
| FR-LIB-005 | 法规库应支持名称、文号、条款、正文摘要、有效状态和关联指标维护。 |
| FR-LIB-006 | 已用于正式评估的指标不得直接物理删除，只能停用或新建版本。 |

### 8.4 静态风险评估

| 编号 | 需求 |
| --- | --- |
| FR-STA-001 | 静态评估应加载 31 项指标并按 8 个类别分组展示。 |
| FR-STA-002 | 每项应展示危险因素、可能导致的事件、现行措施、计划措施和法规依据。 |
| FR-STA-003 | 评估人员应能选择落实状态，填写现场说明，并上传照片或文件证据。 |
| FR-STA-004 | 系统应显示已完成数量、总数量、完成率和未完成项。 |
| FR-STA-005 | 未落实项应自动进入问题候选清单，不得仅以总达标率替代逐项问题记录。 |
| FR-STA-006 | 静态结果应显示各类别问题数、风险等级和高风险项。 |

### 8.5 动态风险评估

| 编号 | 需求 |
| --- | --- |
| FR-DYN-001 | 动态评估应加载 61 项指标，并按进场、装卸、搬运及人、物、环境、管理分类。 |
| FR-DYN-002 | 每项应支持参数录入；参数可采用数值、单选、多选、布尔、文本、日期或附件类型。 |
| FR-DYN-003 | 系统应支持从内置指标数据和经校验的 Excel 文件加载动态评估内容。 |
| FR-DYN-004 | 每项应支持选择可能性 L 和严重度 C，系统实时计算 R=L×C。 |
| FR-DYN-005 | 用户修改 L、C 或关键参数后，风险值、颜色、等级和矩阵落点应立即更新。 |
| FR-DYN-006 | 每项应显示法规依据，并允许填写现场说明和上传证据。 |
| FR-DYN-007 | 未完成必填项时不得提交最终结果；系统应明确指出缺失项。 |

### 8.6 专业人员评估

| 编号 | 需求 |
| --- | --- |
| FR-EXP-001 | 每个评估任务应能够指定安全工程师和项目经理。 |
| FR-EXP-002 | 两类专业人员应分别提交意见、建议等级、重点问题、整改建议和提交时间。 |
| FR-EXP-003 | 系统计算结果与专家意见应并列保存，专家意见不得覆盖原始评分。 |
| FR-EXP-004 | 专家建议与系统等级不一致时，应填写差异理由并在结果页突出显示。 |
| FR-EXP-005 | 专家意见提交后如需修改，应保留修改历史。 |
| FR-EXP-006 | 专家评分如何进入综合结果应采用可配置、可版本化的规则，具体权重待确认。 |

### 8.7 综合风险结果

| 编号 | 需求 |
| --- | --- |
| FR-RES-001 | 系统应汇总静态结果、动态结果和专家意见，生成任务级综合结果。 |
| FR-RES-002 | 结果页应展示综合等级、综合得分、静态达标情况、动态风险分布和专家意见状态。 |
| FR-RES-003 | 系统应展示 5×5 风险矩阵，并可定位落入每个格子的具体指标。 |
| FR-RES-004 | 系统应展示重大、较大、一般、低风险的数量和占比。 |
| FR-RES-005 | 系统应生成问题清单，每项问题包含来源、描述、风险等级、法规依据和证据。 |
| FR-RES-006 | 每项问题应给出详细整改建议，至少包括立即措施、整改步骤、责任建议、期限建议、所需证据和复评要求。 |
| FR-RES-007 | 系统应支持打印或导出完整评估报告；导出内容应与当前权限和筛选条件一致。 |
| FR-RES-008 | 风险规则、指标版本或专家意见未满足提交条件时，结果应标记为未定稿，不得显示为正式闭环。 |

### 8.8 整改任务与进度管理

| 编号 | 需求 |
| --- | --- |
| FR-REC-001 | 正式确认的评估问题应自动生成整改任务，无需重复录入。 |
| FR-REC-002 | 整改任务应包含问题描述、风险等级、整改措施、责任人、协作人、整改期限、资金、预案和证据要求。 |
| FR-REC-003 | 每类问题应支持独立的整改阶段模板，不得只使用统一的百分比输入框。 |
| FR-REC-004 | 阶段模板应包含阶段名称、顺序、完成百分比和完成条件，并允许管理员配置。 |
| FR-REC-005 | 例如“安全帽佩戴”问题可设置“无人佩戴、少数佩戴、多数佩戴、全部佩戴”等阶段；实际百分比映射由业务人员配置。 |
| FR-REC-006 | 页面应以进度环或同等清晰方式展示当前完成度，颜色随阶段变化。 |
| FR-REC-007 | 整改责任人每次更新应填写时间、阶段、进展说明、剩余问题，并可上传照片或文件。 |
| FR-REC-008 | 更新保存后，授权用户应能立即看到最新进度、更新人和更新时间。 |
| FR-REC-009 | 系统应保留完整时间线，不得用最新记录覆盖历史进度。 |
| FR-REC-010 | 逾期未完成、进度停滞或高风险问题应在仪表盘中显著提醒。 |
| FR-REC-011 | 整改任务应支持退回补充、重新提交和复评，退回原因必须记录。 |

### 8.9 双人复核与销号

| 编号 | 需求 |
| --- | --- |
| FR-CFM-001 | 整改责任人完成整改后应发起复核申请。 |
| FR-CFM-002 | 安全工程师应进行技术复核，可确认通过或驳回并填写意见。 |
| FR-CFM-003 | 项目经理应进行管理确认，可确认通过或驳回并填写意见。 |
| FR-CFM-004 | 只有安全工程师和项目经理均确认通过，问题才可标记为已闭环。 |
| FR-CFM-005 | 任一方驳回后，任务应退回整改中，并保留驳回原因和历史确认记录。 |
| FR-CFM-006 | 高风险问题销号前应要求上传规定的整改后证据，并完成必要的风险复评。 |
| FR-CFM-007 | 一个评估任务的全部问题闭环后，任务方可变更为已闭环。 |

### 8.10 历史数据库与查询

## 10 核心业务规则

### 10.1 风险计算

- 单项动态风险值：`R = L × C`；
- L 和 C 均采用 1 至 5 级；
- 风险等级分为重大、较大、一般、低四级；
- 风险等级阈值应在系统中集中配置并版本化，评估记录保存当时的规则版本；
- 修改评分后应重新计算受影响的单项结果、汇总结果、矩阵位置和问题清单；
- 系统分值、专家意见和最终确认应分别保存，避免结论来源不清。

### 10.2 闭环规则

- 评估问题形成后必须指定责任人和期限；
- 整改完成度由问题对应的阶段模板计算，不能由用户任意填写一个无依据的百分比；
- 每次进度更新必须形成不可覆盖的历史记录；
- 安全工程师和项目经理均确认后方可销号；
- 任一复核人驳回即回到整改中；
- 未闭环问题不得从历史统计中消失。

### 10.3 数据版本规则

- 指标、法规、风险阈值、综合算法和整改模板均应具备版本；
- 新版本只影响新建任务，已开始或已完成的任务继续使用原版本；
- 如需对历史任务重算，应由管理员明确发起，并生成新的计算版本和审计记录。

8. 专家意见页；

10. 整改任务列表与整改详情页；
11. 双人复核页；
12. 历史记录与数据分析页；
13. 用户、角色、指标、法规、模板和系统配置后台。

### 11.2 视觉与交互原则

- 延续现有蓝色主基调和项目 Logo，但增加白色、深灰及风险红、橙、黄、蓝作为功能色，避免页面只使用单一蓝色；
- 风险颜色必须同时配合文字和图标，不能只依靠颜色传达状态；
- 页面应体现铁路运输和安全管理场景，整体风格专业、克制、科技化；
- 评估页应优先保证信息密度、快速填写、固定关键操作和清晰进度；
- 长表格应支持分组、筛选、展开详情和固定表头；
- 保存、提交、复核、驳回和销号等关键动作应有明确反馈；
- 删除、作废、退回等高影响操作应二次确认并说明影响；
- 桌面端为主要使用环境，同时适配常见平板和手机查看、进度更新场景；
- 图表不得遮挡标签，数值、单位、时间范围和风险图例必须清晰可读。

### 11.3 演示版信息架构

默认入口为公开产品门户，门户横向导航为“首页、平台概况、业务流程、产品功能、平台特点、产品展示”，并在顶部、首屏、内容区和页脚提供“进入管理平台”入口。管理平台一级导航固定为“安全总览、风险评估、整改闭环、历史分析、基础资料”，用户与通知入口位于全局顶栏。各业务模块职责如下：

| 一级模块 | 首版页面 | 核心任务 |
| --- | --- | --- |
| 安全总览 | 安全驾驶舱 | 查看今日态势、风险分布、待办、趋势和重点任务，并下钻到对应记录 |
| 风险评估 | 任务列表、评估工作台、综合结果 | 完成静态检查、动态 L/C 评分、专家意见、矩阵分析和问题生成 |
| 整改闭环 | 整改任务、整改详情、复核确认 | 分派责任、按阶段更新进度、提交证据、双人复核和销号 |
| 历史分析 | 历史档案、趋势分析、维度分析 | 组合检索历史记录，通过折线图、雷达图、散点图查看变化并下钻 |
| 基础资料 | 指标库、法规库、模板配置 | 维护带版本的指标、法规、风险规则和整改阶段模板 |

演示版默认提供一个可追溯的模拟场站数据集，用于完整演示导航、筛选、下钻、风险计算和进度更新。模拟数据必须在界面中标识为“演示数据”，不得与正式生产数据混淆。

### 11.4 门户首页与驾驶舱要求

- 门户首屏使用通栏科技场景图、项目名称、核心价值和管理平台入口，首屏下方保留下一内容区的可见提示；
- 门户依次展示面包屑、平台概况、业务流程、产品功能、平台特点、产品展示和页脚；
- 门户与管理平台必须可双向返回，手机端导航收纳为可开关菜单；
- 门户顶部、首屏、功能区和页脚的“进入管理平台”入口统一打开登录/注册弹层，不得绕过认证流程直接切换业务页面；
- 登录弹层支持账号和密码校验；注册弹层支持账号、密码和确认密码校验，注册完成后可切换登录；
- 开发版必须提示当前连接的 FastAPI/MySQL 环境；正式版不得将服务端认证描述为浏览器本地演示；
- 临时占位素材必须在页面上明确标注“临时占位”及替换计划，不得作为正式交付素材；

- 进入管理平台后，驾驶舱显示当前组织、数据更新时间和“演示数据”环境标识；
- 顶部核心指标至少包含综合风险指数、重大/较大风险、整改闭环率和逾期任务；
- 风险分布、近 7 次评估趋势、重点风险任务和整改进度应在常见桌面分辨率下一屏或一次短滚动内可见；
- 核心指标卡、图表数据点和任务行应可点击下钻，禁止只做不可操作的展示图；
- 风险等级必须同时使用颜色、文字和图形标记；
- 移动端保留总览、任务查看、整改进度更新和通知入口，复杂批量评估允许提示使用桌面端。

### 11.5 关键交互状态

每个业务页面必须明确提供加载中、空数据、筛选无结果、保存中、保存成功、保存失败和无权限状态。演示版前端使用模拟数据时，也必须保持与未来 API 一致的异步状态接口，不得将成功结果写死在按钮事件中。

## 12 非功能需求

### 12.1 安全性

- 全站使用 HTTPS；
- 密码采用可靠的单向摘要算法存储；
- 服务端必须进行权限校验和输入校验，不得仅依赖前端控制；
- 对登录、导出、附件上传和批量导入进行限流与安全校验；
- 附件应限制文件类型和大小，并防止上传文件被直接执行；
- 日志和页面不得暴露密码、密钥、数据库连接信息等敏感内容；
- 正式数据的导出、作废、规则修改和用户权限变更必须写入审计日志。

### 12.2 性能与可用性

- 常用列表、任务详情和仪表盘在约定数据规模下应快速打开；具体响应时间、并发数和数据规模在部署前确定；
- 长时间填写的评估页面应支持暂存，避免会话过期造成全部内容丢失；
- 保存失败时应保留用户当前输入并给出可操作的错误信息；
- 关键计算应由服务端复核，避免仅在浏览器中计算导致结果不一致；
- 系统应提供健康检查、错误日志、数据备份和恢复流程。

### 12.3 兼容性与部署

- 系统应以网页形式访问，并支持主流现代浏览器；
- 正式环境的访问地址、网络范围、是否面向互联网及身份认证方式需单独确认；
- 开发、测试和正式环境应分离；
- SQLite 可继续用于单机演示，正式多用户部署是否升级为 MySQL 或其他服务型数据库，应依据并发、备份和运维条件决定；
- 可视化库可采用 ECharts 或同等能力方案，但不得依赖不稳定的外部公共 CDN。

### 12.4 可维护性

- 评估指标、法规、风险阈值和整改阶段应通过配置或后台维护，不应散落在页面代码中；
- 关键算法应有自动化测试，并覆盖阈值边界、空值、重复提交和状态流转；
- 数据库升级应提供迁移和回退方案；
- 正式发布应记录版本号、发布时间、变更内容和对应数据库版本。

## 13 验收标准

### 13.1 核心流程验收

1. 管理员能够创建用户并分配评估、整改、复核等角色；
2. 发起人能够创建一个包含静态和动态内容的完整评估任务；
3. 系统能够加载 31 项静态指标和 61 项动态指标，并显示对应法规依据；
4. 修改 L、C 后，单项风险值、等级颜色、矩阵位置和汇总数量同步变化；
5. 安全工程师和项目经理能够分别提交意见，系统保留两者记录；
6. 评估完成后自动形成逐项问题和详细整改建议；
7. 问题能够自动转入整改模块，并使用对应阶段模板显示进度环；
8. 每次进度更新均可在时间线中追溯，旧记录不会被覆盖；
9. 安全工程师和项目经理均确认后问题才可闭环，任一驳回应退回整改；
10. 全部问题闭环后，评估任务能够进入已闭环状态；
11. 历史页面能够检索该任务，并查看原评估、整改证据和复核记录；
12. 折线图、雷达图和散点图能够随筛选条件更新，并能下钻到明细；
13. 越权访问、未登录访问和无权限导出均被阻止并留下必要日志；
14. 对同一正式任务重复提交、重复复核不会产生重复隐患或重复销号记录。

### 13.2 数据验收

- 指标数量、编号、类别、法规依据与经过确认的源表一致；
- 风险矩阵每个边界值均通过测试；
- 汇总数量与逐项明细一致；
- 图表统计结果能追溯并核对到原始记录；
- 历史任务在指标库升级后仍按原版本正确显示；
- 备份文件能够在测试环境完成恢复验证。

### 13.3 界面验收

- 默认打开产品门户，可从门户进入管理平台，也可从管理平台返回门户；
- 未认证时点击任一“进入管理平台”入口均显示登录/注册弹层，错误账号、短密码和两次密码不一致均有明确提示；
- 新用户可完成注册并使用该账号登录，登录成功后进入驾驶舱并显示当前登录账号；
- 门户在 1440 × 900 与 390 × 844 视口下无水平滚动、标题裁切、导航遮挡或图片溢出；
- 主要页面无文字重叠、截断、按钮遮挡和不可读图表；
- 风险状态除颜色外同时提供文字标识；
- 常用分辨率下侧边栏、表格、弹窗和关键按钮可正常使用；
- 评估中断后重新进入能够继续填写已暂存内容；
- 关键操作结果有明确成功或失败提示。

## 14 版本优先级建议

### 14.1 演示版必须完成

- 登录、用户中心和基础角色；
- 评估任务统一流程；
- 静态 31 项、动态 61 项及法规查看；
- L/C/R 计算、风险矩阵和综合结果；
- 安全工程师、项目经理意见与双人确认；
- 自动问题清单、详细整改建议；
- 问题专属阶段、进度环、整改记录和闭环；
- 历史记录和基础折线图、雷达图、散点图；
- 网页部署和数据备份。

### 14.2 后续增强

- 高级统计分析、同类场站对标和自动文字洞察；
- 更细的数据权限、消息提醒和批量导入导出；
- 移动端现场拍照和离线暂存；
- 图片隐患识别、训练数据管理和模型评估。

材料中提出“国庆节形成一版”的时间意图。正式排期前应锁定演示日期、演示环境和“必须完成”范围，避免将图片识别等研究性功能纳入首版阻塞项。

## 16 需求完成定义

本需求在以下条件全部满足后可进入正式开发基线：

1. 待确认事项中的风险阈值、动静态流程、综合算法和专家参与规则已由业务负责人确认；
2. 静态与动态指标源表完成编号、法规、文字和数量校核；
3. 演示版范围、完成日期和部署环境已确定；
4. 页面原型或现有页面改造清单已评审；
5. 核心流程验收用例已由项目组和安全专业人员共同确认。
