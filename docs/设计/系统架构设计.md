# 铁路危险货物运输“双重预防机制”一体化信息平台架构设计

## 1. 架构目标

本架构面向“可演示、可继续开发、可替换模拟数据”的第一阶段。当前先完成网页前端和业务闭环演示，后续接入服务端时保持页面、领域模型和接口契约稳定。

核心约束：

- 风险评估、专家意见、整改和复核记录分别保存，不互相覆盖；
- 指标、阈值、法规和整改模板全部版本化；
- 正式记录采用状态流转和审计记录，不做物理删除；
- 风险计算在前端即时反馈，服务端提交时必须再次计算并校验；
- 图片识别仅提供建议，必须经人工确认才能成为正式隐患。

## 2. 总体分层

```text
浏览器 / 平板 / 手机
        |
        v
React + TypeScript + Vite（frontend/src）
  产品门户（默认入口） -> 登录/注册弹层 -> 进入管理平台
  安全运营平台 -> 页面视图 -> 领域组件 -> API 适配层
        |
        | HTTP / JSON + Bearer JWT
        v
FastAPI（backend/app）
  身份权限 -> 评估服务 -> 整改服务 -> 分析服务 -> 文件服务 -> 审计服务
        |
        v
MySQL 8（SQLAlchemy + PyMySQL）
  users / auth_sessions / 评估任务 / 风险项 / 整改记录 / 审计记录
```

## 3. 前端架构

前端包含两个体验层：公开产品门户负责项目介绍、流程与能力展示；安全运营平台负责风险评估、整改、复核和分析。两层由同一 React 应用承载，共享品牌资产、设计令牌和后续身份会话；业务数据仅在管理平台展示。

技术基线采用 React、TypeScript、Vite、Recharts 和 Lucide 图标；服务端采用 FastAPI、SQLAlchemy、PyMySQL、PyJWT 和 bcrypt。目录职责：

```text
frontend/src/
  components/       通用布局、图表容器、状态标签、模态框
  data/             演示数据，后续由 API 响应替代
  pages/            总览、评估、整改、历史分析、资料页
  types/            领域类型和接口 DTO
  App.tsx            门户/管理平台入口、页面状态和导航
  api/auth.ts        注册、登录、当前用户、退出登录 API 客户端
  App.css            管理平台布局和业务组件样式
  Portal.css         产品门户响应式布局与视觉样式

backend/
  app/main.py        FastAPI 应用、CORS、健康检查和启动生命周期
  app/auth.py        注册、登录、当前用户、退出和修改密码接口
  app/models.py      User、AuthSession 及后续领域模型
  app/database.py    SQLAlchemy Engine、Session 和依赖注入
  app/security.py    bcrypt 密码摘要和 JWT 签发/解析
  docker-compose.yml MySQL 8.4 开发实例（宿主机 3307）
```

页面不得直接依赖后端字段细节。API 适配层负责 DTO 到领域模型的转换。当前门户以登录/注册弹层拦截所有“进入管理平台”入口，前端通过 FastAPI 认证 API 获取 JWT，令牌只保存在当前会话的 sessionStorage；用户、密码摘要和登录会话保存于 MySQL，前端页面切换、组件隐藏和本地状态均不承担授权职责。正式部署前仍需配置生产密钥、HTTPS、限流、审计和更细粒度的角色/数据范围权限。

## 4. 服务端模块边界

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| 身份与权限 | 登录、令牌、组织、角色、数据范围 | 服务端鉴权，前端隐藏不等于授权 |
| 评估中心 | 任务、静态检查、动态评分、专家意见、综合结果 | 幂等提交；保留规则与指标版本 |
| 整改中心 | 问题生成、分派、阶段进度、证据、复核、销号 | 双人复核；更新记录不可覆盖 |
| 分析中心 | 趋势、分布、矩阵、排行和下钻 | 每个聚合结果可回溯明细 |
| 基础资料 | 指标、法规、阈值、整改模板 | 发布后生成新版本，不覆盖历史版本 |
| 文件与 AI | 附件、摘要、图片识别结果、人工复核 | 类型/大小校验；AI 结论不得直接生效 |
| 审计与通知 | 操作日志、待办、站内通知 | 高影响动作记录前后值和操作者 |

## 5. 核心状态机

### 5.1 评估任务

`草稿 -> 静态评估 -> 动态评估 -> 待专家意见 -> 待确认 -> 已形成问题 -> 整改中 -> 待复核 -> 已闭环`

任一必填项、规则版本或专家意见不完整时，任务只能保存为草稿或未定稿。重复提交使用任务 ID 与提交版本做幂等校验。

### 5.2 整改问题

`待分派 -> 待整改 -> 整改中 -> 待安全工程师复核 -> 待项目经理确认 -> 已闭环`

任一复核人驳回后回到“整改中”，保留驳回意见和原复核记录。阶段百分比来自问题类型对应的模板，不允许任意填写无依据的百分比。

## 6. 核心数据实体

主实体包括 `Organization`、`User`、`AssessmentTask`、`IndicatorVersion`、`AssessmentItem`、`ExpertOpinion`、`HazardIssue`、`RectificationTask`、`ProgressRecord`、`ReviewRecord`、`Attachment`、`RuleVersion` 和 `AuditLog`。

所有业务主表使用不可变唯一 ID，并保存 `created_at`、`updated_at`、`created_by` 和版本号。评估明细额外保存当时的指标文本、法规快照和阈值版本，防止基础资料升级后历史结果发生变化。

## 7. 首批 API 契约

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/dashboard/overview` | 驾驶舱指标、趋势、分布和重点任务 |
| GET/POST | `/api/assessments` | 查询、新建评估任务 |
| GET | `/api/assessments/{id}` | 获取任务、指标、意见和结果 |
| PUT | `/api/assessments/{id}/items/{itemId}` | 暂存单项参数与证据 |
| POST | `/api/assessments/{id}/submit` | 幂等提交并由服务端复算 |
| GET | `/api/rectifications` | 组合筛选整改任务 |
| POST | `/api/rectifications/{id}/progress` | 追加进度记录 |
| POST | `/api/rectifications/{id}/reviews` | 提交复核或驳回意见 |
| GET | `/api/analytics/*` | 趋势、矩阵、维度和散点数据 |
| GET | `/api/master-data/*` | 获取指标、法规、规则与模板版本 |

响应统一包含 `requestId`、`data`、`error` 和服务端时间。列表使用游标或页码分页；更新接口携带版本号实现乐观锁。

## 8. 权限模型

首版角色：系统管理员、评估发起人、安全工程师、项目经理、整改责任人、只读观察员。权限由“角色能力 + 组织数据范围 + 任务参与关系”共同决定。

高影响动作包括规则发布、正式提交、驳回、销号、导出、作废和权限调整，必须二次确认并写审计日志。

## 9. 部署演进

### 阶段 A：交互演示

Vite 构建静态站点，数据由本地模拟服务提供。用于界面评审和业务规则确认，不承载正式数据。

### 阶段 B：联调试用

前后端分离部署，接入测试数据库和对象存储；启用身份认证、权限、审计、迁移、自动化测试和备份任务。

### 阶段 C：生产上线

在明确用户量、网络边界、等保/合规要求和运维责任后确定数据库、负载均衡、容灾与监控方案。上线前完成真实设备、浏览器、权限、恢复和安全测试。

## 10. 当前实现与后续工作

当前仓库实现阶段 A：官网式产品门户、FastAPI + MySQL 认证链路、门户与管理平台双向入口、响应式布局、业务导航、交互式风险评分、矩阵、整改进度和历史图表。已实现注册、登录、当前用户、退出和修改密码 API；评估、整改和分析业务仍使用前端演示数据，尚未接入后端领域接口。门户中的参考站公开图片仅为布局演示占位，正式交付前需替换为自有或已授权素材。阶段 B 之前仍需由业务负责人确认风险阈值、综合算法、指标源表和正式部署边界。
